# 健康测评系统 — 后端架构设计（Schema + API）

> 项目：better-me（【睿迄科技】全栈开发 3 天挑战）
> 数据库：Supabase（PostgreSQL + Auth + RLS）
> 框架：Next.js 16 (App Router) + TypeScript
> 本文档为 Schema 与 API 的落地设计，供评审后进入实现。

## 0. 技术栈定案

- **数据库**：Supabase（托管 PostgreSQL）
- **ORM/访问**：`@supabase/supabase-js`（官方 SDK），数据库类型由 CLI 生成到 `database.types.ts`
- **迁移**：Supabase CLI `supabase db push` + `migrations/` SQL 文件（每个迁移一棵 SQL），`migrations/*.sql` 是** schema 独立真相源**
- **本地开发**：本地 docker 完整 Supabase 栈（`supabase start`），行为与云端一致，迁移后用 `supabase db push` 同步到云端
- **鉴权**：Supabase Auth
  - **匿名登录**（Anonymous Sign-in）→ 生成随机 `user_id`，充当「随机 UserID / 简易 Session 识别」，零门槛，无需注册
  - **正式账号**：付费前把匿名身份**升级**为正式账号（邮箱+密码），用 `auth.updateUser({ email, password })`，需开启**手动链接身份（manual linking）**。付费记录绑正式账号，清 cookie 重登录可找回。
- **RLS**：所有表开启 Row Level Security，按 `auth.uid()` 隔离用户数据。`@supabase/ssr` 管 cookie 会话。

> 重要：**`auth.users` 是 Supabase 托管的用户表**，我们业务表用 `user_id` 外键引用它，**不重复建业务用户表**。用户（含匿名）之所以能当“用户”，是因为 Supabase Auth 已维护好身份。

> **service_role key 绝不能暴露给浏览器**，仅用于无需用户上下文的系统级操作（本题尽量不用）。

## 1. 领域建模

用一个**会话（assessment_session）**贯穿整个问卷，这是核心聚合根。用户一次性问卷产生的数据都挂在会话下；订阅状态关联到**用户（auth.users）**（用户级，非会话级）。

### 实体关系总览

```
auth.users (Supabase 托管用户表) ──1:N── assessment_session
      │                                  │
      │                                  ├──< assessment_answer  (step 答案，每步一行)
      │                                  │
      │                                  ├──1:1── assessment_result  (计算结果)
      │
      └──1:N── subscription (订阅状态，用户级，N 天有效)
```

- `auth.users` 是 Supabase 托管的用户表（含匿名用户与正式账号），业务表用 `user_id` 外键引用，**不重复建业务用户表**。
- 一个用户可开多个 session（重新测评）。
- 一个 session = 一次完整的问卷流。
- 每个 step 的增量答案存 `assessment_answer`（答一题 insert/update 一行）。
- 所有数据填完后计算 `assessment_result`。
- `subscription` 记录**该用户（user）的会员订阅**，N 天有效；用户级权益，非会话级。

> **定案：订阅绑 user（用户级订阅）。** 理由：①产品是「会员天数制」——充值 N 天，N 天内该用户名下**所有**问卷结果都解锁，天然是用户级权益；②判断某 session 是否解锁 = 查**该 session 所属 user** 的 subscription 是否在有效期内（`starts_at <= now <= expires_at`），与 session 无关。③「已付费测试 sessionId」用于演示——该 session 所属用户已付费，付费前后对比依然成立。
>
> 判断「本次 session 是否付费」：查该会话归属的 user 的 `subscription`，看当前时间是否在 `[starts_at, expires_at]` 内。`是` → 返回完整；`否` → 返回脱敏。

## 2. Schema（表结构）

### 2.1 assessment_session（测评会话 — 核心）
| 字段 | 类型 | 说明 |
|---|---|---|
| id | uuid PK | 随机 uuid，即「sessionId」，给前端/演示用 |
| user_id | uuid FK → auth.users | **直接挂用户**（不再经 profile），RLS 依据 |
| status | text | in_progress / completed |
| current_step | int | 已进行到第几步（进度恢复用，服务端推导，不信任客户端） |
| quiz_version | text | 题库版本（如 'v1'），记住这次用的是哪版题库 |
| started_at / updated_at | timestamptz | |

> **定案：去掉 `assessment_profile`**（Advisor 指出它现在只剩 user_id + 时间戳，冗余），直接把 `user_id` 放在 `assessment_session` 和 `subscription` 上。

> 表名用 `assessment_*` 前缀，与 Supabase 内置 `auth.*`、`storage.*` 区分。

### 2.2 assessment_answer（分步答案）
| 字段 | 类型 | 说明 |
|---|---|---|
| id | uuid PK | |
| session_id | uuid FK → assessment_session | |
| step_key | text | 如 `age`,`height`,`weight`,`target_weight`,`activity_frequency`…（**枚举用常量集中定义**） |
| answer_value | jsonb | 灵活存单选/多选/数值（如 `{"value":"30-39"}` 或 `{"kg":72}`） |
| answered_at | timestamptz | |
| UNIQUE(session_id, step_key) | | 同一步重复提交 = update（幂等，处理重复提交/乱序） |

> 用 `jsonb` 而不是每个字段一列：因为问卷是**动态多步**，step 数量/字段可扩展（DB 可扩展性）。但题目要求的**身体数值**（身高/体重/目标体重）与最终计算强相关，会在 result 计算时用**显式列**或从 jsonb 里解析，二选一说明：这里用 jsonb 存储原始答案（灵活、进度恢复用），计算时后端解析出严格校验过的数值。

### 2.3 assessment_result（计算结果）
| 字段 | 类型 | 说明 |
|---|---|---|
| id | uuid PK | |
| session_id | uuid FK → assessment_session | 1:1 |
| bmi | numeric(5,2) | 计算值 |
| bmi_category | text | underweight/normal/overweight/obese |
| recommended_calories | int | 建议摄入量（kcal/天） |
| target_date | date | 目标预测日期 |
| prediction_curve | jsonb | **预测曲线数据**（这里存完整值；返回给前端时按订阅状态决定脱敏与否） |
| algorithm_version | text | 算法版本（如 'v1'），记住这次是用哪版算法算的 |
| calculated_at | timestamptz | |

> `prediction_curve` 是「被保护字段」的典型：**DB 里存完整**，API 层根据订阅状态决定返回完整还是打码。这样非会员的脱敏逻辑在 API 层（且可测试），DB 不需要冗余两份。

### 2.4 subscription（订阅状态 · 用户级）
| 字段 | 类型 | 说明 |
|---|---|---|
| id | uuid PK | |
| user_id | uuid FK → auth.users | **挂用户**（不是 session） |
| status | text | inactive / active |
| starts_at | timestamptz | 订阅生效时间 |
| expires_at | timestamptz | 订阅到期时间（N 天后） |
| payment_event_id | text | 支付事件唯一 ID，**UNIQUE**，幂等用 |
| paid_at | timestamptz | 支付时间 |
| amount | numeric(10,2) | 模拟金额（可选） |

> **定案：订阅挂 user_id（用户级天数制）**。一个用户一条订阅记录，`[starts_at, expires_at]` 窗口内有效。判断某 session 是否解锁 = 查该 session 归属用户是否存在有效订阅（`status=active` 且 `now` 在窗口内）。
>
> 校验逻辑归一：`isUnlocked = status==='active' && starts_at <= now && now <= expires_at`。
>
> **续期（不缩短）**：`expires_at = greatest(coalesce(expires_at, now()), now()) + interval 'N days'`——若当前已过期则从 now 重算 N 天，若未过期则在原有到期日**顺延 N 天**，避免重复续期把有效期缩短。
>
> **幂等**：同一 user 重复 `/pay` → upsert（重复调用不重复生效/不报错）。用 `payment_event_id`（UNIQUE）保证支付事件唯一。

## 2.6 题库与文案：代码配置（非数据库）

**定案：题库（题目/选项/feedback 文案）放代码里的结构化 TS 配置（`lib/quiz/`），不进数据库。**

理由：题库是**应用内容**（所有人一样、基本静态），不是**用户数据**（每人不同、实时变化）。用户数据才进数据库；应用内容放代码配置，除非需要运营免代码换文案/A/B 测试（本题不涉及）。

好处：
- **Types 静态类型**：每个选项的 `feedback` 字段类型上就要求非空，编译期拦下「忘配文案」。
- **文案与逻辑集中**，改文案不动逻辑；可用测试断言每个选项都有 feedback。
- 版本随代码走，可 review、可测试。

```ts
// lib/quiz/config.ts —— 集中配置，前后端共用一份契约
export const QUESTION = {
  weightChange: {
    stepKey: "weight_change",
    question: "你的体重通常怎么变化？",
    options: [
      { value: "gain_fast_lose_slow", label: "增重快但减得慢",
        feedback: "这正是我们最擅长处理的，很多人卡在这个点上。" },  // ← 选它就显示这句
      { value: "gain_lose_easily", label: "增减都容易",
        feedback: "你的代谢很灵活，调整方案见效会很快。" },
      { value: "struggle_gain", label: "很难增重或长肌肉",
        feedback: "我们会把重点放在增肌和力量上。" },
    ],
  },
  // ...
} as const;
```

**feedback 预存储与边界覆盖**（对应 Q4）：反馈挂选项，不挂问题——选什么反馈什么，天然差异化。

| 边界 | 对策 |
|---|---|
| 某选项忘配 feedback | 全局 default 兜底文案 |
| 数值输入（身高/体重） | 按区间归类给文案；BMI 偏高/正常/偏低各有鼓励 |
| 极值/离群值（如身高 200cm） | 区间判断 + 软化文案（安抚不冒犯），同时走数据校验拒绝非法值 |
| 用户没选直接下一步 | 前端「选完才进下一步」强制，防跳过 |
| 多选问题 | 反馈取第一个选的，或给一句总体文案 |
| 缺失字段 | 反馈不依赖缺失值；缺失值在计算层走校验报错 |

> 测试兜底：断言每个选项都有非空 feedback、每个数值区间都有对应文案。

## 2.7 匿名登录：静默 + 渲染与持久化分离

**定案：用 Supabase 匿名登录充当「随机 UserID / 简易 Session 识别」。但：①首屏立即渲染不阻塞；②匿名登录**成功前不做任何持久化保存**——不允许后端接受未认证的客户端自造 sessionId（会绕过 RLS/归属校验，Advisor 指出）。**

- 匿名登录是轻量 POST（无邮箱/手机验证、不弹窗），几十毫秒返回。
- 页面挂载时**后台并行**调匿名登录，同时立即渲染第一题（不阻塞首屏）。
- **第一次持久化保存（POST step）必须在匿名登录成功之后**：成功后才请求 `/api/session` 开正式会话。
- 登录失败：提示重试，或进入**显式非持久模式**（仅本地浏览，不写库）。
- 用 `@supabase/ssr` 管理 cookie 会话。

> **Cookie 归属澄清（Advisor）**：Supabase 的**身份 token（含 `auth.uid()`）存在 cookie 里**，由 `@supabase/ssr` 维护。`sessionId` **不是用户身份**、不必权威存 cookie——它只用于导航/识别一次问卷，恢复会话靠「按 `assessment_session.user_id = auth.uid()` 查」。升级正式账号后清 cookie，重新登录（邮箱+密码）即可找回所有 session + 订阅。

### 2.7.1 订阅前升级正式账号（定案）

**漏斗：匿名填问卷 → 结果脱敏 → 点「解锁」→ 升级/注册弹窗 → 变成正式账号 → 付费 → 订阅绑正式账号 → 结果完整。**

前提：在 Supabase 开启**匿名登录** + **手动链接身份（manual linking）**。

升级技术：当前匿名会话活跃时调用 `supabase.auth.updateUser({ email, password })`，把邮箱/密码身份链接到当前用户。**这保留了同一个 `auth.users.id`**，所以已填的答案、session 都还挂在原 user_id 下，不丢失。

**已拍板决策：**
- **已有账号：仅新建/升级**。若输入邮箱已属于其他账号 → 升级失败；遇到此情况引导用户「先登录已有账号再来」，不做会话认领/合并（避免 3 天范围内高风险的数据合并冲突）。
- **邮箱确认：关闭**（演示简化）。输入邮箱即生效，付费立即可用；README 写明这一权衡（生产会要求邮件确认）。本地 Supabase 会用 Inbucket 抓确认邮件，想测确认时仍可测。

```
POST /api/upgrade  body: { email, password }
  → 要求当前已登录（匿名）用户，`auth.updateUser({ email, password })` 升级为正式账号
  → 成功 → 返回 { ok:true }
  → 若 email 已属于其他账号 → 400，提示先登录已有账号
```

### 2.7.2 `/api/pay` 拒绝匿名

**定案：`/api/pay` 必须拒绝匿名用户**，只允许已升级且（未强制确认时）已存在的正式账号调用。匿名用户无稳定身份，付费记录无意义。

- 判定：当前 user 的 `email` 非空（或非 `is_anonymous`）才算正式账号。
- 若仍匿名 → 403，提示先升级/登录。

## 3. API 设计（Next.js Route Handlers）

统一挂 `/api` 下。所有接口都对 sessionId 或 user 上下文做校验。

### 3.1 会话生命周期

| 方法 | 路径 | 作用 | 请求体 | 响应 |
|---|---|---|---|---|
| POST | `/api/upgrade` | （订阅前置）匿名用户升级为正式账号 | `{ email, password }` | `{ ok }` |
| POST | `/api/session` | 开新会话（**匿名登录成功后**调用） | `{}`（user 从 session/RLS 取） | `{ sessionId, currentStep }` |
| GET | `/api/session/[id]` | 进度恢复：返回已填答案 + 当前步 | — | `{ sessionId, currentStep, answers }` |
| POST | `/api/session/[id]/step` | 分步保存：每步增量提交 | `{ stepKey, answerValue }` | `{ ok, currentStep }` |
| POST | `/api/session/[id]/complete` | 全部填完，触发计算 | `{}`（答案**从库读**，不接受应答前端传整个 answers） | `{ resultId }` |

> **complete 不接收整个 answers**：答案从 Supabase 读已持久化的记录，避免前端提交的数据与已存数据不一致（Advisor 指出）。请求体只 `{}`。

> **current_step 由服务端推导**：取「连续完成的必填步骤」的最高步（不是客户端报的最大步，也不是已提交 step 数的粗暴 max）。后端用题库配置判定哪些 step 已连续完成。

### 3.2 结果与订阅

| 方法 | 路径 | 作用 | 说明 |
|---|---|---|---|
| GET | `/api/session/[id]/result` | 结果页数据 | **按订阅状态差异化返回**：非会员 `prediction_curve` 打码/隐藏 + `locked: true` + 提示付费；会员完整 + `locked: false`。**判断基准**：当前用户是否有**有效订阅**（status=active 且 now 在 [starts_at, expires_at] 内） |
| POST | `/api/pay` | 模拟支付回调（**用户级，拒绝匿名**） | `{}` | `{ ok, expiresAt }` |
| (get) | `/api/session/[id]/subscription` | 查订阅状态 | — | 判断「脱敏→完整」 |

### 3.3 契约字段（枚举单源）

题目强调「契约字段一开始钉死」。所有 step 的 key 与枚举值用 TS 常量集中定义（`lib/steps.ts`），后端校验 + 前端使用同一份，Test 引用常量，避免魔法字符串漂移。

## 4. 核心健康评估算法（服务端）

提交后由服务端计算，结果持久化到 `assessment_result`：

- **BMI** = 体重(kg) / (身高(m))²
- **BMI 分类**：<18.5 underweight；18.5–24.9 normal；25–29.9 overweight；≥30 obese
- **建议摄入量（kcal/天）**：用 Mifflin-St Jeor 基础代谢率 BMR 估算，再按活动频率乘系数：
  - 男：`10×体重 + 6.25×身高(cm) − 5×年龄 + 5`
  - 女：`10×体重 + 6.25×身高(cm) − 5×年龄 − 161`
  - × 活动系数（1.2 sedentary / 1.375 light / 1.55 moderate / 1.725 active）
  - 再按目标调整（减重 −500 约每周减 0.5kg）得到建议摄入
- **目标预测日期**：由（目标体重 − 当前体重）与减重速率（如每周 0.5–1kg 安全区间）推算日期
- **预测曲线**：按周生成一条「体重随时间」的预测序列（数组），存 jsonb

> 这是「服务端计算逻辑」，必须做成纯函数模块（`lib/health/assess.ts`），便于单元测试边界：极端值、缺失字段、非法身高/体重/年龄、目标体重不合理（如≤0 或高于当前体重的减重目标）等。

## 5. 鉴权与差异化返回设计

### 5.1 数据归属
- 匿名登录后，Supabase 给一个 `user_id`（auth.uid()）。
- `assessment_session` 直接存 `user_id = auth.uid()`；`subscription.user_id = auth.uid()`。
- `sessionId` 用于恢复，但**仍必须校验归属**（按 `user_id = auth.uid()` 查），防止越权访问他人 session。

### 5.2 差异化返回（结果接口的真实逻辑）
```
GET /api/session/[id]/result
  校验 session 归属当前 user（user_id = auth.uid()）
  查当前 user 的 subscription（status=active 且 now 在 [starts_at, expires_at] 内）
  if isUnlocked:
    return { locked:false, data:{...完整 result, prediction_curve: 完整数组} }
  else:
    return { locked:true, message:"解锁完整预测", data:{
        ...result,
        prediction_curve: masked_curve,   // 打码/隐藏核心预测
        // 仅返回非敏感字段
    }}
```

> 关键测试点：**非会员拿不到被保护的 `prediction_curve` 完整值**。测试断言非会员响应里曲线是打码或不存在完整值；会员拿到完整值。
>
> **判断基准是「当前用户的订阅」，不是 session 的**——因为订阅是用户级。同一用户任意 session 的 result 在订阅有效期内都是完整的。

### 5.3 模拟支付（拒绝匿名）
```
POST /api/pay  body: { }
  → 鉴权当前调用者（Supabase user）
  → **拒绝匿名用户**：若 email 为空 / is_anonymous → 403，提示先升级/登录
  → upsert 该 user 的 subscription：status='active', starts_at=now()
       expires_at = greatest(coalesce(expires_at, now()), now()) + interval 'N days'
  → 幂等：以 payment_event_id 唯一，重复调用不重复生效
  → 返回 { ok:true, expiresAt }
```
> 前端触发后重新请求 result → 得到完整态，形成「脱敏→完整」闭环。
>
> **服务端用匿名用户的 client（带 cookie），不要用 service_role 做 /pay**（避免把 service_role 暴露给浏览器 / 绕过归属校验）。service_role 仅用于无需用户上下文的系统级操作。

> **升级/登录触发点**：结果页 `locked:true` 时，前端引导用户「解锁 → 升级账号/登录 → 付费」。升级用 `auth.updateUser({ email, password })`（保原 user_id，数据不丢）。若邮箱已被占用 → 提示先登录已有账号。

## 6. RLS 策略（要点）

| 表 | 策略 |
|---|---|
| assessment_session | `user_id = auth.uid()` for select/insert/update |
| assessment_answer | 经 session.user_id 关联 `auth.uid()`（join session） |
| assessment_result | 经 session.user_id 关联 |
| subscription | `user_id = auth.uid()`（用户级） |

> 服务端 API Route 用匿名用户的 client（带 cookie），RLS 生效，这是**主链路**。service_role 仅用于不含用户上下文的系统级操作（本题尽量不用）。

## 10. 决策定案（已拍板）

1. **订阅语义：用户级**（充值 N 天，N 天内该用户名下所有问卷结果都解锁）。subscription 挂 `user_id` + `starts_at`/`expires_at`。判断解锁基准是「当前用户的订阅」，不是某个 session。
2. **jsonb vs 显式列**：原始答案 jsonb（灵活可扩展）+ 计算值落 result 显式列（bmi/calories/target_date/curve）。
3. **/pay 归属**：需鉴权当前调用者 + **拒绝匿名用户**（要求正式账号）；用匿名用户 client（带 cookie）不用 service_role。README 提供「已付费测试 sessionId」演示。
4. **题库/文案：代码配置**（`lib/quiz/`），不进数据库。
5. **匿名登录：静默异步 + 持久化前置**（登录成功前不写库，后端不接收未认证的自造 sessionId）。身份存 cookie；`sessionId` 非身份，恢复靠「按 user_id 查」。
6. **无独立 profile 表**：去掉 `assessment_profile`，`user_id` 直接放 session/subscription（避免冗余）。
7. **版本化**：session 存 `quiz_version`，result 存 `algorithm_version`，答案存原始值（不存渲染后文案），反馈按版本 + 配置重建。
8. **current_step 服务端推导**：连续完成的必填步，不信任客户端。
9. **complete 不接整个 answers**：从库读已持久化记录。
10. **订阅前升级**：匿名→正式账号（`auth.updateUser`，保原 user_id 不丢数据）；**已有账号仅新建/升级**（不做会话认领合并）；**邮箱确认关闭**（演示简化，README 写权衡）。需开手动链接身份。
11. **订阅续期不缩短**：`expires_at = greatest(coalesce(expires_at, now()), now()) + N天`；`payment_event_id` 唯一保幂等。
12. **本地开发 + 迁移到云端**：本地 docker 完整 Supabase 栈（`supabase start`），`migrations/*.sql` 为唯一真相源，`supabase db push` 同步云端。
